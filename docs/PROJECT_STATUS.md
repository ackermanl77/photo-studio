# Project Status

## Architecture

```text
Streamlit frontend (app/frontend_unified_app.py)
        |  HTTP (multipart POST /process, JSON options)
        v
Flask processing backend (app/backend.py, 127.0.0.1:8502)
        |
        v
PhotoProcessor + feature modules
        |
        v
Pillow / NumPy / OpenCV / scikit-image / optional rawpy
```

`app/backend.py` is the app's processing engine: `frontend_unified_app.py` no longer calls `PhotoProcessor` for edits directly. Each tab only captures control values into an `options` dict; once per rerun, `app/backend_client.py::process_via_backend()` sends the source image (plus the combined mask and/or layer overlay, when present) to `/process` and the response becomes the canvas/export image. `app/backend.py::process_image()` starts with ICC normalization (converts an embedded, non-sRGB profile into sRGB via `app.professional_color.normalize_to_srgb()` — not a UI-visible step, runs unconditionally whenever the source has an embedded profile) and then applies the rest of its steps in the exact order the tabs appear (Lens → Tone → Color → Detail → Layers → Masks → Portrait → Crop) — keep that order in sync with the frontend if either changes; a mismatch reproduces the class of bug described in "Recently Fixed" below. `PhotoProcessor` is still used directly, locally, for three things that don't belong on the network round trip: decoding the uploaded file (including RAW), building mask geometry against the un-edited source, and face detection for the Portrait tab's caption.

`app/desktop.py` starts the backend as a child process and waits for `/health` before starting the Streamlit child, so the desktop app always has a live backend. Running the frontend standalone (`streamlit run app/frontend_unified_app.py`, without `desktop.py`) also works: `ensure_backend_running()` starts `python -m app.backend` on demand the first time it's needed and caches that check for the life of the Streamlit server process (`st.cache_resource`). Because every Streamlit rerun would otherwise repeat a full HTTP round trip with the whole image, `frontend_unified_app.py` wraps the backend call in `st.cache_data`, keyed on the exact image/options/mask/layer bytes — reruns triggered by unrelated controls (zoom, Show Original) don't re-hit the network. Large images will still feel slower than the old in-process path on the *first* rerun after a real edit; there's no way to fully avoid that round trip without changing the UI's interaction model (e.g. debouncing sliders), which is out of scope for now.

The desktop wrapper is `app/desktop.py`, and the PyInstaller specification is `PhotoStudio.spec`.

## Primary Entry Points

| Purpose | Entry point |
|---|---|
| Unified application (the only Streamlit UI) | `app/frontend_unified_app.py` |
| Command-line single-image / folder batch processing | `app/cli.py` (run as `python -m app`) |
| Desktop wrapper (packages the unified app in a native window; starts the backend too) | `app/desktop.py` |
| Processing backend the frontend talks to over HTTP | `app/backend.py` |
| HTTP client + on-demand backend startup used by the frontend | `app/backend_client.py` |

Earlier development iterations used additional per-feature Streamlit entry points (`frontend_project.py`, `frontend_layers.py`, `frontend_masking.py`, `frontend_batch.py`, `frontend_library_editor.py`, `frontend_portrait.py`, `frontend_diagnostics.py`, `frontend_release.py`, `frontend_complete.py`, `frontend_center.py`, `frontend_integrated.py`, `frontend_unified_v2.py`, `integrated_workbench_next.py`, and plain `frontend.py`). They were consolidated into `frontend_unified_app.py` and **no longer exist** in `app/` (their compiled `.pyc` files are the only trace left, in `app/__pycache__/`). Any documentation that still tells you to run one of them describes a past development snapshot — see the notice at the top of `docs/workflows/README.md`.

## Recently Fixed

- **Layers and Masks were silently discarded from the final image.** In `app/frontend_unified_app.py`, every tab's code runs on every Streamlit rerun regardless of which tab is visible, and each tab reassigned the same `edited_image` variable. Because the Portrait tab ran last in source order (and its skin-smoothing slider defaulted to `0.2`, not `0`), the canvas preview and the exported file were always `smooth_skin(processor.image, p_smooth)` — which never included the Layers composite (its result was only written to a local variable, never back into `processor.image`), and always applied skin smoothing whether or not the user opened that tab. **Fixed**: the Layers tab now writes its composite back into `processor.image`; the Portrait slider now defaults to `0` (no change) and only mutates `processor.image` when the user opts in; and a single `edited_image = processor.image` line right after all tabs (not one per tab) now feeds the canvas and export, so the final image reflects Tone → Color → Detail → Layers → Masks → Portrait cumulatively regardless of tab order. Verified with a standalone script exercising `PhotoProcessor`/`LayerWorkspace`/`smooth_skin` directly.
- **RAW files were not actually usable from the unified UI.** The uploader accepted `.cr2/.cr3/.nef/.arw/.dng`, but the uploaded bytes were loaded with `PIL.Image.open()` directly, which cannot decode camera RAW. **Fixed**: the upload now goes through `PhotoProcessor.from_bytes(uploaded.getvalue(), uploaded.name)`, which routes RAW extensions through `app.raw_import` (`rawpy`) and everything else through the same PIL path as before. If `rawpy` isn't installed, the app now shows a clear `st.error()` message (from the existing `RuntimeError`) instead of crashing. Verified: non-RAW uploads behave identically to before, RAW extensions are correctly routed, and the missing-`rawpy` case raises the expected friendly error.
- **Only one mask could be active at a time in the unified UI.** The Masks tab was a single dropdown (Luminance/Color/Gradient/Radial) with no way to combine selections, even though `app.advanced_masks.MaskStack`/`MaskLayer` (union of several named, enable/disable-able, invertible, opacity-weighted masks) already existed and was tested. **Fixed**: the Masks tab now lets you add any number of named mask layers (each with its own type-specific parameters, invert, opacity, and edge softening), toggle or remove them individually, and preview the combined selection as a red overlay; `MaskStack.combined()` unions the enabled layers into one mask before the Target Exposure/Contrast/Saturation sliders are applied. Verified with a standalone script: two non-overlapping mask layers (a luminance selection and a radial selection) each contribute their own region to the union, a disabled layer's contribution disappears, and the masked adjustment only changes pixels inside the combined selection.
- **`streamlit-drawable-canvas` was a dead dependency.** It was listed in `pyproject.toml` and `requirements.txt`, and pulled into the PyInstaller build in `PhotoStudio.spec` (hidden imports, its frontend `build/` assets bundled, `collect_all("streamlit_drawable_canvas")`), but was never imported anywhere under `app/` — pure install and build-size overhead. **Fixed**: removed it from `pyproject.toml`, `requirements.txt`, and `PhotoStudio.spec` (all the canvas-specific hidden-import/data-collection code). While in `PhotoStudio.spec`, also fixed a second stale reference in the same file: its `hiddenimports` still listed `"app.frontend"`, which hasn't existed since the frontends were consolidated (same issue as the desktop.py bug fixed earlier) — updated to `"app.frontend_unified_app"`. Verified `pyproject.toml` parses and no longer lists the dependency, `requirements.txt` no longer references it, and `PhotoStudio.spec` still has valid Python syntax after the edit.
- **Cropping / aspect-ratio fitting had no control in the unified UI.** `PhotoProcessor.fit_aspect_ratio()`/`.crop()` existed and were CLI-accessible, but the Streamlit app never called them. **Fixed**: added a new "⛶ Crop" tab (after Portrait, before Presets, so it runs after Masks in tab-execution order and never sees a size mismatch against masks built from the pre-crop image) with an aspect-ratio selector (Square, 4:5, 5:4, 3:2, 16:9, 9:16, or Original/no crop) that calls `processor.fit_aspect_ratio()`, center-cropping the cumulative image from every earlier tab. Verified with a standalone script that `fit_aspect_ratio` is idempotent (re-applying the same ratio to an already-cropped image is a no-op) so the reactive (button-less) Streamlit rerun model can't drift the crop on every interaction.
- **`app/frontend_unified_app.py`'s tab composition had no automated regression coverage.** Every fix listed above (layers/masks dropped from the final image, RAW not decoded, single-mask limit, missing crop control) was the kind of bug that only a test driving the actual composed script — not the individual processing functions in isolation — would catch. **Fixed**: `tests/test_frontend_unified_app.py` now drives the real app through Streamlit's `AppTest` harness (`from streamlit.testing.v1 import AppTest`), simulating an uploaded image via `file_uploader.set_value()` and asserting on the rendered output. It covers the no-image `st.stop()` path, all 9 tabs rendering without exceptions, a layer actually changing the composited canvas image, a combined mask's target-exposure adjustment reaching the final image, the Crop tab changing output dimensions, and Undo restoring a prior control value.
- **`app/backend.py` was a fully-built, tested processing API that nothing called.** `app/desktop.py` never started it and `app/frontend_unified_app.py` called `PhotoProcessor` directly in-process instead — the exact "second copy of the pipeline" this doc used to warn about. **Fixed**: the frontend now routes its whole edit pipeline through `app/backend.py`'s `/process` endpoint via the new `app/backend_client.py` (see "Architecture" above); `app/desktop.py` starts the backend as a child process before the Streamlit child. Two things had to change on the backend side to make this safe: `process_image()` was reordered to match the frontend's tab order exactly (it previously applied saturation and highlights/shadows in a different order than the UI, and preset after sharpen instead of right after Tone — silently produces a different image than what the tabs implied), and `validate_image_bytes()` (PIL-only) is now skipped for RAW filenames so RAW uploads don't get rejected before reaching `PhotoProcessor.from_bytes()`'s RAW-aware path. The backend also gained the two capabilities the frontend needed that it didn't have yet: layer compositing (`layer` file + `layer_opacity`/`layer_blend` options) and portrait skin smoothing (`portrait_smoothing` option). The Batch Processor and Library Catalog in the "More" tab were deliberately left as-is (still in-process) — routing batch work through the backend was considered and explicitly deferred. Verified with new tests in `tests/test_backend.py` (layer compositing, masks seeing the post-layer image, portrait smoothing, RAW upload no longer 400s) and `tests/test_backend_client.py` (backend auto-start, HTTP round trip against a real backend instance).
- **Undo/Redo and Save/Load Project were implemented as library code but never wired into the UI.** `app.edit_history.EditHistory` and `app.project.PhotoProject` existed and were tested in isolation, but `app/frontend_unified_app.py` never used them. **Fixed**: every control (Tone/Color/Detail/Masks/Portrait/Crop settings plus the mask-layer list) is captured into one JSON-serializable "recipe" dict (`_build_recipe()`); the Presets tab now records a recipe snapshot into a session-scoped `EditHistory` on every rerun (deduped automatically, so only real changes create a step) and exposes Undo/Redo buttons, and a "Save Project" button bundles the recipe, the original source image, and (if present) the uploaded overlay layer into a downloadable `.photoproject` file via `PhotoProject.save()`. A new "Open a saved project" uploader above the image uploader restores a `.photoproject` via `PhotoProject.load()`. Because Streamlit forbids writing to a widget's `session_state` key after that widget has already been created in the current run, both Undo/Redo and Load Project write the target recipe into a `_pending_restore` session_state entry and call `st.rerun()`; a new block at the very top of the script (before the image uploader) applies `_pending_restore` into every widget's session_state key before any widget is instantiated. Verified with a standalone script: a `.photoproject` saved with a recipe (including a base64-encoded layer payload) round-trips byte-for-byte through `PhotoProject.save()`/`.load()`, and `EditHistory.undo()`/`.redo()` cycle correctly across multiple recorded snapshots, including truncating the redo branch after a new edit follows an undo. (Save/Load Project has since moved off `PhotoProject` onto `ProjectBundle` -- see the entry below.)
- **Save/Load Project used the simpler single-layer `PhotoProject` format instead of the more complete `ProjectBundle` (v2) format.** `ProjectBundle` existed and was tested, but nothing outside its own tests used it — the overlay layer was instead base64-embedded directly into the recipe dict as a workaround, and `PhotoProject.load()` has no archive hardening (no entry-count/size/path-traversal checks) unlike `ProjectBundle.load()`, which calls `app.reliability.validate_project_archive()` first. **Fixed**: Save Project now builds a real `app.layer_workspace.LayerWorkspace` from the overlay (background = source, one added `WorkspaceLayer` for the overlay) and stores its `.to_json()` in `ProjectBundle.layer_workspace`, instead of the base64-in-recipe hack; Load Project reads `ProjectBundle.layer_workspace_object()` back and translates its second layer (index 0 is always the `LayerWorkspace`-internal "Background") into the same `recipe["layer"]` shape `_restore_recipe_to_state()` already expected, so that function needed no changes. Mask-layer *definitions* (the parametric Luminance/Color/gradient/Radial params, not rendered mask images) deliberately stay in `recipe["mask_layers"]` as before rather than moving into `ProjectBundle.masks` — they're cheap to recompute against the source image on load and staying parametric keeps them re-editable after reopening a project, which baking them to PNG would lose. `ProjectBundle.load()` is backward compatible with old `PhotoProject`-saved files (its v1/v2 manifest handling already tolerates the missing `layers`/`masks` keys), so existing `.photoproject` files from before this change still open. Verified with new tests in `tests/test_frontend_unified_app.py` (Save Project completes without error with a layer attached; Load Project restores recipe values and the layer's opacity/blend/image from a real `ProjectBundle` file; an old-format `PhotoProject` file still loads) and live in the running app (saved/reloaded a project with a multiply-blended layer and confirmed opacity, blend mode, and the composited canvas all matched).

- **Full ICC profile conversion and soft proofing — the last two items on the "what would a professional editor do" gap list.** Previously the app just preserved whatever `icc_profile` bytes a file happened to carry, unlooked-at, and applied every tonal/color operation as if the pixels were already sRGB — for a wide-gamut source (Adobe RGB, ProPhoto RGB, a camera's own profile) that's subtly wrong: colors that were correct under the wider profile look oversaturated once treated as sRGB.   Soft proofing deliberately does **not** simulate an external printer/press profile — what that usually means in Lightroom/Photoshop needs a calibrated profile file (e.g. a press house's own `.icc`) this offline-first app has no database or bundled copy of (the same "no real profile database" limitation already true of Lens Profiles above). ## Known Issues

- ICC soft-proofing targets this app's own sRGB working space, not a real printer/press profile -- there's no profile database or bundled `.icc` file (see "Recently Fixed"), the same limitation already true of Lens Profiles above.
- The denoise algorithm (Non-Local Means, via OpenCV) is a real, meaningful upgrade over the flat median filter it replaced, but it is classical/non-learned, not a neural network -- see "Recently Fixed" for why, given this app's CPU-first, no-GPU-dependency, no-heavy-new-dependency constraints.
- Lens corrections aren't calibrated to any specific camera/lens model — there's no real profile database (see "Recently Fixed"); `LENS_PROFILES`'s entries are generic starting points by lens category, not anything matched against a photo's actual EXIF lens metadata (which isn't read at all currently).
- Every edit now costs one HTTP round trip with the full image to `app/backend.py` (mitigated by `st.cache_data`, see "Architecture" above, but not eliminated). Large photos will feel slower to edit than before the backend was wired in.
- The Masks tab's "Preview combined mask overlay" checkbox (and Repair's "Preview removal selection") draws the red/yellow selection over `_lens_corrected_source()` — the un-edited source with only Lens corrections applied, matching the geometry Masks/Repair/Crop actually operate against (see "Recently Fixed") — not the live Tone/Color/Detail/Layers result. That further-edited intermediate image only exists on the backend, and re-fetching it just for this debug preview wasn't judged worth another round trip per rerun.
- The backend's per-request cache (`_cached_process_via_backend`, keyed on the full `options` dict) doesn't isolate the denoise step from cheaper options that come later in the pipeline (Repair/Layers/Masks/Portrait/Crop) — changing any of those still forces a full Non-Local Means recompute even though denoise's own input didn't change. A real fix needs the backend pipeline split into cacheable stages (e.g. a "through Detail" stage feeding a cheap "Repair onward" stage), which is a genuine architecture change deliberately deferred rather than rushed — see "Recently Fixed".
- The HSL Color Mixer's "always render all 8 bands" fix for Streamlit's widget-garbage-collection-on-non-instantiation bug, `_request_rerun()`/`_rerun_pending`, and the hidden-textarea commit pattern (curve editor, paint editor) are three independent, inline solutions to the same underlying problem, with no shared helper between them — flagged in the code review above and deliberately left as-is rather than forcing a redesign of the HSL UI to unify them.
- Full ICC profile conversion and soft proofing are not implemented; embedded profiles are preserved where supported.
- The normal working pipeline is primarily 8-bit RGB; 16-bit TIFF export exists but does not make every adjustment operation 16-bit internally.
- Face detection gracefully degrades when the installed OpenCV build lacks Haar cascade support.
- Microsoft Edge WebView2 Runtime is required for the native desktop window.
- The Library Catalog's keyboard shortcuts (rate/reject/navigate) only work while a real browser tab has the page focused — they reach into `window.parent.document` from a `components.html()` iframe, which `streamlit.testing.v1.AppTest` (a headless harness with no real DOM/JS) can't exercise, so that part is only covered by live manual verification, not the automated suite. The same limitation now also applies to the draggable free-form crop rectangle and the tone curve's click-to-add/drag/double-click-to-remove extra points — their JS interactions are covered by live verification and by driving the hidden commit field directly (the same wiring a real interaction ultimately depends on), not by an automated test that simulates an actual drag or double-click.
- The on-canvas paint editor (including re-editing an existing "Painted" selection's "🎨 Edit Painting") draws at a downscaled preview resolution (capped at 480px on the long edge via `preview_image()`), not the source's full resolution — fine for the bilinear upscale `MaskLayer.normalized()` already does for every mask kind, but a very precise, high-resolution brush edge will look softer than a pixel-perfect selection would.
- Dehaze's transmission map is smoothed with a plain Gaussian blur, not a real edge-aware guided filter (see "Recently Fixed") — expect a faint halo around strong, hard edges at high strength. There's also no sky segmentation, so a hazy sky can receive more correction than the rest of the scene.
- Magic Wand samples a single pixel's color at the click point with no averaging over a small neighborhood (unlike some tools' "sample size" option) — a click that happens to land on a noisy/anti-aliased pixel can select a narrower or wider region than expected; adjusting Tolerance compensates.
- The histogram clipping-warning overlay uses fixed thresholds (a channel at exactly 0 or 255) with no adjustable margin, and — like the Masks/Repair preview overlays and the ICC gamut warning — is a locally-computed debug preview over the already backend-processed `edited_image`, not a separate network round trip.
- Vibrance's skin-tone protection is a fixed hue-range heuristic (~25 degrees, no adjustable center/width), not real face or skin detection — an unrelated orange/tan subject (wood, terracotta, autumn leaves) gets the same reduced boost a genuine skin tone would.
- `estimate_white_balance()`'s closed-form correction is derived from a linearized (cross-term-dropped) version of `apply_temperature_tint()`'s own formula — exact for a pixel already close to neutral (the intended use: click something that's *supposed* to be gray or white), but only an approximate starting point for a pixel with a severe color cast, the same caveat darktable's own picker carries ("often it works really well," not "always exactly").
- `correct_perspective()`'s two axes (Vertical/Horizontal Keystone) are applied as independent sequential warps rather than one combined homography solve — visually indistinguishable from a combined solve in practice, but means the "untouched" edge of a single-axis correction isn't perfectly pixel-identical to the source (a homography that fixes only 2 of a quadrilateral's 4 corners doesn't leave the line between them pointwise-fixed), just far less changed than the edge actually being corrected.
- Applying a saved custom preset across a Batch Processor run intentionally skips that preset's `mask_layers`/`removal_mask_layers`/overlay layer — see `app/recipe_options.py::recipe_to_options()`'s docstring for why (they're tied to one specific photo's pixel coordinates) — so a preset built around a local mask adjustment will only carry its global tone/color/detail/lens settings into the batch, not the local one. A Free-form crop box is excluded from batch application for the same reason, even though — unlike masks/layers — it's stored size-independently (as fractions) and so could in principle be translated per-photo if a future caller had each batch photo's own dimensions on hand at conversion time.
- The draggable free-form crop rectangle only offers two corner handles (top-left, top-right's and bottom-left's positions follow implicitly) plus drag-the-body-to-move — there's no independent handle on every corner/edge, and a resize is clamped to a minimum 2% of the frame in each dimension so the box can't be dragged down to zero-size.
- The tone curve's "extra" points can be added and dragged freely in both X and Y, but there's no visual warning while dragging one directly onto another point's exact X — the collision is only caught and silently resolved (the earlier-sorted point wins, the later one is dropped) when the curve is actually applied, in `app.recipe_options.merge_curve_points()`.
- Film Grain is unseeded (a fresh random pattern on every edit/export) — deliberate, so repeated exports of the same photo don't carry an identical, visibly repeating texture, but it also means the exact grain pattern isn't reproducible across two separate exports of the same settings.
- Post-Crop Vignette and the Lens tab's corrective vignette are independent controls that both run in the same pipeline (Lens's before Crop, Effects' after) — using both at once stacks their darkening/brightening rather than one overriding the other, which is the expected behavior for two conceptually different tools but can look like "double vignetting" if not intentional.
- "Color Noise" has no effect while Denoise is 0 (the slider is disabled to make this visible) — it's a modifier to Non-Local Means' existing `hColor` parameter, not an independent chroma-only denoise pass, so it can't run without Denoise also being nonzero.
